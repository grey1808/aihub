# Корпоративный ИИ-помощник

Веб-приложение, которое ставится на один компьютер (моноблок) внутри компании.
Сотрудники заходят на него по сети из браузера, регистрируются и задают вопросы
в чате. Помощник отвечает, опираясь на документы компании и данные из 1С,
и показывает, откуда взял ответ.

Всё работает локально: нейросеть крутится на том же компьютере, никакие данные
наружу не уходят. Интернет нужен один раз — при установке.

---

## Что умеет

**Сотрудник** открывает браузер и попадает в чат. Больше ему ничего знать не надо:
ни что такое база знаний, ни где лежат документы, ни как устроена 1С.
Он спрашивает «за сколько дней подавать заявление на отпуск» — и получает ответ
со ссылкой на документ, из которого этот ответ взят.

В чат можно приложить файл, картинку или надиктовать голосом:

* **Документы** (pdf, docx, txt, csv и другие) — помощник читает их и отвечает
  по содержимому: «какой срок оплаты в этом договоре».
* **Голосовые** — расшифровываются моделью Whisper, расшифровка показывается
  в сообщении. Можно вообще ничего не печатать: надиктовал и отправил.
* **Картинки** — фото документа, скриншот. Нужна модель со зрением
  (`LLM_VISION_MODEL`); без неё помощник честно скажет, что смотреть картинки
  ему нечем, а не сделает вид, что посмотрел.

Файлы можно выбрать кнопкой, перетащить в окно или вставить из буфера (Ctrl+V).
Интерфейс рассчитан и на телефон: список чатов уезжает в выдвижное меню,
поле ввода не прячется под панелью браузера, кнопки крупные.

**Профиль и личная память.** В профиле сотрудник указывает, как к нему обращаться
и кем работает — помощник учитывает это в каждом ответе: бухгалтеру и кладовщику
на один и тот же вопрос нужны разные ответы.

Там же лежат **заметки помощника** — личная память об этом сотруднике, которую
помощник читает перед каждым ответом, в любом чате. Работает как `agent.md`,
только своя у каждого пользователя:

> — Запомни, что я веду учёт по ООО «Ромашка», а отчёты мне нужны таблицей.
> — Запомнил.

Дальше, в том числе в новых чатах, помощник это учитывает. Заметки можно
править руками в профиле. Их не видит никто, кроме самого сотрудника —
ни коллеги, ни администратор.

**Администратор** (логин `admin`) в админке подключает источники данных:

| Тип источника | Что это |
|---|---|
| Папка с файлами | Каталог с документами: pdf, docx, txt, md, csv и другие |
| Сетевая папка Windows (SMB) | Общая папка `\\server\share` по логину и паролю |
| Confluence | Вики от Atlassian, та же учётка, что у Jira. Cloud и Server |
| База данных 1С (SQL) | Прямые запросы `SELECT` к СУБД, на которой работает 1С |
| 1С через OData | Штатный REST-интерфейс 1С — понятнее и безопаснее прямого SQL |
| Веб-страницы | Список адресов внутреннего портала |

Вложения в чате в базу знаний **не попадают**: это разовые файлы конкретного
сотрудника, а не общая база. Чужое вложение не увидит никто, включая
администратора — переписка с помощником считается личной.

Источников может быть сколько угодно — их количество нигде не зашито.
Каждый тип источника — это один класс в `app/Knowledge/Connectors/`,
который сам описывает свои поля; админка рисует форму по этому описанию.
Чтобы добавить седьмой тип источника, шаблоны править не нужно.

## Как это работает внутри

```
Сотрудник                                   Админ
   │                                          │
   │ вопрос                                   │ настраивает источники
   ▼                                          ▼
┌──────────────┐   ищет по смыслу   ┌──────────────────────┐
│   Чат (web)  │◄──────────────────►│  База знаний         │
└──────┬───────┘                    │  Postgres + pgvector │
       │                            └──────────▲───────────┘
       │ вопрос + найденные фрагменты          │ индексация по расписанию
       ▼                                       │
┌──────────────┐                    ┌──────────┴───────────┐
│  Нейросеть   │                    │ Коннекторы:          │
│ Ollama / LM  │                    │ файлы, SMB,          │
│   Studio     │                    │ Confluence, 1С, web  │
└──────┬───────┘                    └──────────────────────┘
       │ может сама сходить в 1С за свежими цифрами
       ▼
  ответ + ссылки на документы
```

Два механизма работают вместе:

1. **Поиск по документам (RAG).** Документы режутся на фрагменты, каждый
   переводится в вектор и кладётся в Postgres с расширением pgvector.
   Перед каждым вопросом система сама ищет подходящие фрагменты — векторным
   и полнотекстовым поиском одновременно — и подкладывает их модели.
   Это делается **до** обращения к модели: полагаться на то, что модель сама
   догадается вызвать поиск, нельзя — небольшие модели этого не делают.

2. **Инструменты агента.** Модель дополнительно может сама выполнить запрос
   к 1С (`SELECT` или OData), поискать ещё раз другими словами или посмотреть
   список источников. Карту источников — что где лежит и как этим пользоваться —
   она получает из описаний, которые заполнил администратор.

## Управление пользователями

Регистрация открыта: сотрудник заходит на страницу входа, жмёт
«Зарегистрироваться» и заводит учётную запись сам. Должность спрашивается прямо
при регистрации — потом её мало кто дозаполняет.

В админке (раздел «Пользователи») можно:

* завести сотрудника вручную — если не хочется объяснять, как регистрироваться;
* **сменить пароль** — почтового сервера на моноблоке нет, письмом пароль
  не восстановить, так что это единственный способ помочь забывчивому;
* задать короткий логин — входить по `obuh` проще, чем диктовать почту;
* поправить должность и отдел, если сотрудник их не указал;
* выдать права администратора;
* закрыть доступ, не удаляя переписку, или удалить совсем.

Последнего администратора система не даст ни разжаловать, ни отключить,
ни удалить — иначе в админку никто больше не войдёт.

Переписки сотрудников и их личных заметок в админке нет намеренно:
это личные данные.

## Голос, картинки и HTTPS

Три вещи, которые стоит понять до установки.

**1. Голосовые расшифровывает отдельный сервис.** Ollama распознавать речь
не умеет — это другая задача и другая модель. Рядом поднимается контейнер
`whisper`, который говорит по тому же протоколу:

```bash
docker compose --profile with-whisper up -d
```

Модель по умолчанию — `Systran/faster-whisper-small`: быстрая, но на русском
ошибается. Для моноблока со 128 ГБ ставьте крупнее, в `.env`:

```ini
STT_MODEL=Systran/faster-whisper-large-v3
```

**2. Картинки понимает только модель со зрением.** Обычная текстовая модель их
не видит в принципе. Нужна отдельная:

```bash
docker compose exec ollama ollama pull qwen2.5vl:7b
# и в .env:
LLM_VISION_MODEL=qwen2.5vl:7b
```

Пока эта переменная пустая, картинки принимаются и хранятся, но помощник
на них не отвечает.

**3. Запись голоса в браузере требует HTTPS.** Это не наше ограничение,
а правило самих браузеров: микрофон и камера доступны только на защищённых
страницах или на `localhost`. Сотрудник, открывший помощника с телефона
по адресу `http://192.168.1.50:8080`, кнопку записи нажмёт — и получит отказ.

Поэтому на моноблоке HTTPS нужно включить:

```ini
ENABLE_HTTPS=true
APP_SSL_PORT=8443
APP_URL=https://192.168.1.50:8443
```

`deploy/install.sh` сам выпустит самоподписанный сертификат на десять лет.
Отдельно это делается командой `make https`.

Браузер один раз покажет предупреждение «сертификат не является доверенным» —
для самоподписанного это нормально: «Дополнительно» → «Перейти на сайт».
После этого микрофон заработает. Чтобы предупреждения не было совсем,
сертификат нужно добавить в доверенные на каждом устройстве (или выпустить
его внутренним удостоверяющим центром компании, если он есть).

Приложить готовый аудиофайл можно и без HTTPS — ограничение касается только
записи с микрофона прямо в браузере.

## Быстрый старт (на своём компьютере, для проверки)

Нужны только `docker` и `docker compose`.

```bash
cp .env.example .env
# в .env поправьте, если порт 8080 занят:
#   APP_PORT=8081
#   APP_URL=http://localhost:8081
# и возьмите модели полегче:
#   LLM_MODEL=qwen3:4b
#   LLM_EMBEDDING_MODEL=bge-m3

docker compose --profile with-ollama --profile with-whisper up -d --build

# Модели скачиваются один раз, это долго
docker compose exec ollama ollama pull qwen3:4b
docker compose exec ollama ollama pull bge-m3

make diagnose      # проверить, что всё на месте
```

Откройте http://localhost:8080 и войдите как `admin` / `admin`.

Если компьютер слабый, для проверки самой механики хватит совсем маленьких
моделей — `qwen3:0.6b` и `all-minilm` (тогда `LLM_EMBEDDING_DIMENSIONS=384`).
Отвечать содержательно они почти не умеют, но вся цепочка «источник → индекс →
поиск → ответ со ссылками» на них работает и проверяется.

## Установка на моноблок

```bash
git clone <репозиторий> /opt/aihub
cd /opt/aihub
cp .env.example .env
```

В `.env` обязательно поправьте:

```ini
APP_URL=http://192.168.1.50:8080     # адрес моноблока в сети
AUTOSTART_ON_BOOT=true               # поднимать приложение при включении
ADMIN_PASSWORD=<новый пароль>        # не оставляйте admin
DB_PASSWORD=<новый пароль>
LLM_MODEL=qwen3:32b                  # железо тянет — берите крупную модель
LLM_VISION_MODEL=qwen2.5vl:7b        # чтобы помощник видел картинки
STT_MODEL=Systran/faster-whisper-large-v3   # распознавание русской речи
ENABLE_HTTPS=true                    # иначе не будет записи голоса с телефонов
DOCUMENTS_PATH=/mnt/documents        # папка с документами компании
```

Затем:

```bash
sudo ./deploy/install.sh
```

Скрипт соберёт контейнеры, скачает модели, проверит, что всё работает,
и — если `AUTOSTART_ON_BOOT=true` — пропишет автозапуск через systemd.

После этого при каждом включении компьютера приложение и нейросеть поднимаются
сами. Сотруднику остаётся открыть браузер.

```bash
systemctl status aihub        # посмотреть состояние
./deploy/uninstall-autostart.sh   # отключить автозапуск
```

**Про AUTOSTART_ON_BOOT.** Это и есть переключатель из задачи: на моноблоке
`true`, на машине разработчика `false`. Скрипт установки читает его и решает,
ставить systemd-юнит или нет. Сами контейнеры при этом имеют
`restart: unless-stopped` — то есть после падения поднимаются в любом случае,
но без systemd-юнита не запустятся после перезагрузки компьютера.

## Работа без интернета

Интернет нужен ровно один раз — при установке: скачать образы Docker и модели.
Дальше всё работает в изолированной сети.

Если моноблок вообще не увидит интернета, подготовьте всё на другой машине:

```bash
# на машине с интернетом
docker compose --profile with-ollama --profile with-whisper pull
docker compose build
docker save aihub-app pgvector/pgvector:pg16 nginx:alpine redis:7-alpine \
    ollama/ollama fedirz/faster-whisper-server:latest-cpu \
    | gzip > aihub-images.tar.gz

docker compose --profile with-ollama --profile with-whisper up -d ollama whisper
docker compose exec ollama ollama pull qwen3:32b
docker compose exec ollama ollama pull bge-m3
docker compose exec ollama ollama pull qwen2.5vl:7b
docker cp aihub-ollama:/root/.ollama ./ollama-models
# модель распознавания речи качается при первом голосовом — прогрейте её
# заранее, отправив одно голосовое, и заберите кэш:
docker cp aihub-whisper:/root/.cache/huggingface ./whisper-models

# на моноблоке
gunzip -c aihub-images.tar.gz | docker load
# папку ollama-models положить в том aihub_ollama-data
```

## Настройка источников

Админка → **Источники знаний** → **Добавить источник**.

У каждого источника есть поле **«Что здесь лежит»** — это не для красоты.
Его читает сама модель и по нему решает, куда идти за ответом. Пишите
человеческими словами: «приказы и регламенты бухгалтерии, порядок оформления
командировок и авансовых отчётов».

Порядок работы с новым источником: заполнить → **Проверить подключение** →
**Синхронизировать сейчас** → через минуту обновить страницу и посмотреть
историю обновлений внизу.

Дальше источник обновляется сам, с интервалом, который вы задали.
Документы, которые не менялись, не переиндексируются — сравнивается хеш
содержимого.

### Папки с документами

Папки с хоста пробрасываются в контейнер через `DOCUMENTS_PATH` в `.env`
и видны приложению как `/data/documents`. Этот путь и указывается в админке.

Чтобы подключить несколько разных папок, добавьте строки в `docker-compose.yml`
в разделы `volumes` сервисов `app` и `worker`:

```yaml
      - /mnt/buhgalteriya:/data/buhgalteriya:ro
      - /mnt/kadry:/data/kadry:ro
```

и укажите в админке пути `/data/buhgalteriya`, `/data/kadry`.

### 1С

Два способа, и **OData предпочтительнее**:

* **OData** — штатный REST-интерфейс 1С. Имена объектов человеческие
  (`Catalog_Контрагенты`), права работают штатные, доступ к СУБД не нужен.
  Включается в 1С: Администрирование → Публикация на веб-сервере →
  «Публиковать стандартный интерфейс OData».

* **Прямой SQL** — работает всегда, но имена таблиц в 1С нечитаемые
  (`_Document123_VT456`), и модель в них не разберётся сама. Поэтому в карточке
  источника есть поле **«Описание таблиц для агента»** — его нужно заполнить.
  Лучший вариант: попросить программиста 1С сделать несколько SQL-представлений
  с понятными именами и описать их в этом поле.

Агент работает с 1С **только на чтение**. Каждый запрос проходит проверку
(`app/Knowledge/Sql/SqlGuard.php`): разрешены только `SELECT`, один запрос за раз,
с ограничением числа строк. Это первая линия обороны — вторая обязательна:
**заведите отдельного пользователя СУБД с правами только на чтение**.

Если позже понадобится, чтобы агент что-то записывал в 1С, менять придётся
именно эти два места плюс продумать подтверждение действий пользователем.

### Confluence

Для Cloud (`*.atlassian.net`) нужен e-mail и API-токен
(создаётся в профиле Atlassian → Security → API tokens).
Для Server/Data Center — персональный токен или логин с паролем.
В форме выбирается способ авторизации, поля подписаны.

## Обновление

Разработчик вносит правки и отправляет их в git. На моноблоке человек запускает
одну команду:

```bash
./deploy.sh
```

или `make deploy`. Скрипт сам:

1. проверит, что в рабочей папке нет несохранённых правок (и остановится, если есть);
2. заберёт изменения из git и покажет, что именно пришло;
3. пересоберёт образы, если менялся Docker;
4. доустановит зависимости, если менялся `composer.lock`;
5. накатит миграции базы;
6. прогреет кэш и перезапустит приложение с фоновыми процессами;
7. проверит, что приложение отвечает, и прогонит диагностику.

Если приложение после обновления не поднялось, скрипт покажет логи и напишет
команду отката на предыдущую версию.

Два момента, о которых стоит знать:

* **Стили и скрипты собираются заранее.** После правки шаблонов или `resources/js`
  разработчик выполняет `make assets` и коммитит `public/build` — в php-образе
  нет Node, и на моноблоке собрать их нечем. Если забыть, `deploy.sh` предупредит.
* **Новые зависимости требуют интернета.** Если на моноблоке его нет, а обновление
  добавляет библиотеку, скрипт остановится и попросит скопировать папку `vendor`
  с машины разработчика.

## Обслуживание

```bash
make help        # список всех команд
make diagnose    # первое, что стоит запустить при любой жалобе
make logs        # логи приложения и очереди
make sync        # обновить все источники прямо сейчас
make reindex     # переиндексировать базу знаний заново
make test        # прогнать тесты
make https       # включить HTTPS (нужен для записи голоса)
```

**Смена модели эмбеддингов** (`LLM_EMBEDDING_MODEL`) требует полной
переиндексации: у разных моделей разная размерность вектора, старые
и новые векторы несопоставимы.

```bash
# поправить LLM_EMBEDDING_MODEL и LLM_EMBEDDING_DIMENSIONS в .env
docker compose exec app php artisan migrate:fresh --force --seed   # сотрёт всё
make sync
```

**Правки в `.env`** применяются только после пересоздания контейнеров —
обычного `restart` мало, переменные попадают внутрь при создании:

```bash
docker compose up -d --force-recreate app worker scheduler
```

`deploy.sh` делает это сам.

**Логи**: `storage/logs/laravel.log` внутри контейнера и `docker compose logs`.

## Разработка

```bash
# В .env для разработки:
APP_ENV=local
APP_DEBUG=true
```

В режиме `local` контейнер включает перечитывание изменённых PHP-файлов.
В `production` opcache держит код в памяти и правки в браузере **не видны**
до перезапуска контейнера — это сделано намеренно ради скорости.

После правки Blade-шаблонов или стилей: `make assets` (или `make assets-docker`,
если на хосте нет npm). Результат сборки — папка `public/build` — намеренно
лежит в репозитории: в php-образе нет Node, а на моноблоке нет интернета,
собрать там будет нечем. Собрали — закоммитили.

Файл `docker/php/entrypoint.sh` вшивается в образ при сборке — после его
изменения нужен `make build`.

Тесты идут на Postgres (в отдельной базе `aihub_testing`), а не на sqlite:
база знаний держится на расширении pgvector, которого в sqlite нет.

### Где что лежит

```
app/
  Agent/            цикл работы агента, системный промпт, инструменты
    Tools/          поиск по знаниям, список источников, запросы в 1С, память
  Attachments/      приём файлов, расшифровка голоса, подготовка для модели
  Knowledge/
    Connectors/     по одному классу на тип источника
    Contracts/      интерфейс, который реализует коннектор
    Sql/            подключение к чужим БД и проверка запросов на чтение
    SourceSynchronizer.php   забирает документы и кладёт в базу
    TextExtractor.php        достаёт текст из pdf, docx, html, csv
  Llm/              клиент к Ollama / LM Studio
  Rag/              разбиение на фрагменты, индексация, гибридный поиск
deploy/             установщик, сертификат для HTTPS, systemd-юнит
deploy.sh           обновление уже установленного приложения
docker/             образ php, конфиги nginx и php
```

### Добавить новый тип источника

1. Создать класс в `app/Knowledge/Connectors/`, реализовать интерфейс
   `App\Knowledge\Contracts\Connector`: `key()`, `label()`, `help()`,
   `fields()`, `test()`, `documents()`.
2. Добавить его в список в `app/Knowledge/ConnectorRegistry.php`.

Всё. Форма в админке, валидация, шифрование паролей, синхронизация
по расписанию и попадание в базу знаний заработают сами.

## Что стоит доделать

Это рабочая основа, а не законченный продукт. Осознанно не сделано:

* **Распознавание речи на процессоре идёт небыстро.** Минутное голосовое
  моделью `large-v3` на CPU обрабатывается около минуты. Если это окажется
  неудобным, смотрите в сторону модели `medium` или сборки Whisper под видеокарту.
* **Память помощника пишется по явной команде.** Фразу «запомни, что…»
  приложение обрабатывает само и не зависит от модели. Всё остальное
  («помощник сам решил, что это стоит запомнить») работает через инструмент
  `remember` — а значит, зависит от того, насколько уверенно модель вызывает
  инструменты. На `qwen3:32b` это надёжно, на маленьких моделях — нет.
* **Разграничение доступа к источникам.** Сейчас любой зарегистрированный
  сотрудник ищет по всей базе знаний. Если кадровые документы не должны быть
  видны всем — нужны группы пользователей и привязка источников к группам.
* **Потоковый вывод ответа.** Сейчас ответ появляется целиком, после паузы.
  Посимвольный вывод (SSE) сильно улучшит ощущение скорости на больших моделях.
* **Запись в 1С.** Агент только читает.
* **Файлы Excel.** `.xlsx` пока не разбирается — добавляется в `TextExtractor`.
  Вложения в чате это тоже касается.
* **Распознавание текста на фотографиях (OCR).** Сейчас текст с фото читает
  только модель со зрением. Отдельный OCR (tesseract) работал бы точнее
  на сканах документов.
* **Добавление вложения в общую базу знаний.** Кнопки «сохранить этот файл
  в базу знаний для всех» пока нет — только через админку и источники.
